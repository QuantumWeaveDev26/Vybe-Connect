# Chatbot drafts and published versions

The chatbot editor uses **Save draft** and **Publish** as separate operations. Creating a chatbot saves a disabled, unpublished record plus its first draft. Saving settings or graph edits changes only the draft. The published keyword, graph, enabled status, delivery mode and running conversation sessions remain unchanged.

Publishing revalidates the entire graph, current teammate assignments and workspace media/template resources inside one transaction. It writes a new immutable configuration snapshot, installs that version as the active configuration and cancels sessions on the old version. Existing outbox version/resource/consent/window/owner fences still apply; a provider request already submitted cannot be recalled. Publication does not enable server/provider gates.

Each saved draft has a revision and a base published version. Editor saves, restores and publication carry both expected values. Stale requests return HTTP 409 rather than silently overwriting another editor's changes. Unsaved graph edits retain the versions on which they started even if the workspace refreshes in the background. Refresh and review the latest configuration when resolving a conflict.

**Publication history** shows the latest 20 captured versions. **Restore to draft** copies an earlier configuration into a new draft; it does not change the active chatbot. Review settings/resources and publish explicitly to activate a restored configuration. History snapshots include configuration, not provider credentials or the contents of remotely referenced resources. Historical assignments/resources can become invalid; restore/publication revalidation can reject them.

History is append-only through application operations and persists in the private database. Active runtime execution counters are outside the immutable configuration. Existing flows keep their current behavior; the current configuration is captured on their next publication if not already recorded. Earlier overwritten configurations cannot be reconstructed. The older admin `flow.save` API remains a direct publish operation for compatibility, also records snapshots, and invalidates a draft based on the previous published version. New editor workflows do not call that API. Administrators can still delete a chatbot; the retained revision records are inaccessible through the UI after deletion. A general retention/export policy remains separate work.

Local tests cover draft isolation, new-flow inactivity, immutable history, restore-to-draft, optimistic conflicts, stale admin/tenant access, current-member validation, draft preservation of waits and publish-time cancellation. Real browser/device and live Meta acceptance remain unverified. This release does not claim every WATI graph type or exact WATI runtime behavior.
