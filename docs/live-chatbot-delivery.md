# Live chatbot text delivery

Chatbot settings now choose **Create unsent drafts** or **Queue real WhatsApp replies**. Draft mode remains the default. Configuring live mode does not enable the server gate. Real requests additionally require complete and live Meta settings, the exact workspace variable `TW_META_WORKSPACE_ID_FLOW_SEND=true`, a current administrator owning the flow and a real customer message within the preceding 24 hours for text/media; approved templates additionally require current consent and may follow longer waits. Keep the flag false until an approved live test.

The interpreter checkpoints at each message or question. It persists one text job and resumes only after the provider returns an accepted message identifier. A question becomes answerable after its prompt is accepted. Waits following a message begin from actual accepted submission time. Local contact actions run in their graph order between checkpoints. Text/question delivery uses the existing official Cloud API adapter. Media and supported approved-template nodes are now documented in rich-chatbot-delivery.md; external integration nodes remain incomplete.

Job claiming, contact/session checks and continuation use SQLite write transactions. Incoming webhook deduplication and one active checkpoint prevent duplicate enqueue. Competing workers cannot claim the same job. The worker rechecks flow version, enabled state, administrator membership, service window, current inbound ordinal, human control and server gates before sending. Simulated incoming messages produce drafts only and cannot advance an active real checkpoint.

STOP, takeover, edited flows and newer real messages suppress queued requests. A customer message arriving before a question prompt is accepted pauses for human review rather than recording it as an answer. If a gate or window closes, queued work is cancelled and the current checkpoint pauses. It is not silently replayed after re-enabling.

Each provider request is attempted once. A response without a non-empty bounded message identifier is treated as unknown, never as acceptance. Definitive rejection is failed; timeout or lost workers are unknown and pause for human review. A late provider result is retained for reconciliation but never resumes a checkpoint already marked unknown. Provider references are attached to the inbox message so later delivery webhooks can update recorded status. Submission acceptance is not delivery/read confirmation. A request already in flight cannot be recalled; later STOP/settings changes suppress continuation rather than claiming to unsend it.

The latest 50 workspace jobs appear under the selected chatbot. Current message status comes from the bounded inbox sample; no status is invented when it is absent. There is no automatic retry or reconciliation action in this increment. Full production durability, out-of-order webhook reconciliation and immutable published graph versions require further work.

Verification uses temporary databases and mocked Meta transport, including concurrent workers, slow responses, cancellation, real-window gates, simulations and sequence ordering. No real Meta request was made. Live account acceptance, exact WATI behavior and browser visual parity remain unverified. The existing REA captures inform feature vocabulary; live browser access is still unavailable.
